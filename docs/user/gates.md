# Project gates

Gates are the project-local execution entry point generated by `dab init` and `dab normalize`. The runner checks DAB source drift and runs the project's own code and docs commands. Gate files are project-only: global scope never generates them, and gates add no `dab` command.

## Files

| Path | Owner | Purpose |
|---|---|---|
| `.agents/gates.yaml` | authored | Gate modes, commands and project configuration needs. |
| `scripts/dab-check.mjs` | generated | Stable runner; contains no project commands. |
| `scripts/dab-gates.json` | generated | Compiled from `.agents/gates.yaml`; the scanner only seeds a missing starter and never backfills an existing config. |

- `.agents/gates.yaml` is authored source. `dab init` and `dab normalize` create it only when missing and never overwrite it.
- `scripts/dab-check.mjs` carries a `// dab-gate-runner: <version> sha256=<hash>` marker. `scripts/dab-gates.json` records `generated.dabVersion` and a SHA-256 hash of its canonical `gates` object.
- Normalize updates an unmodified older runner or stale snapshot. A modified, unversioned or newer generated file is preserved with a warning; it is never overwritten or downgraded.
- The runner reads only the JSON snapshot. It does not parse YAML and embeds no project commands.

## Requirements

- Node.js `>=24.9` for the runner.
- A DAB binary for the fixed `source` gate. The runner resolves `DAB_BIN`, then `node_modules/.bin/dab`, then `dab` on `PATH`, then `npx --no-install @saydone/dab`; it never installs from the network.
- Project tools such as Xcode, Android SDK, Maven, Gradle or Swift must already be installed. A missing tool makes its command fail; it never becomes a silent skip.

## Configuration

```yaml
version: 1
gates:
  source:
    mode: required
  code:
    commands:
      test:
        command: pnpm test
        mode: required
      typecheck:
        command: pnpm typecheck
        mode: required
      lint:
        command: pnpm lint
        mode: advisory
  docs:
    mode: check
```

- `version` is `1`; an unknown version is a configuration error.
- `source.mode` is always `required` and cannot be disabled.
- `code.commands` accepts `test`, `typecheck`, `lint` and `build`. A command entry has exactly one of `command` or `xcodebuild`.
- `command` is a project-trusted command string run through the platform shell from the project root. `command: null` means the command needs project configuration and is not a pass.
- `xcodebuild` requires exactly one of `project` or `workspace`, plus `scheme` and `destination`; `configuration` is optional. Normalize compiles it to an equivalent `xcodebuild test ...` command in the snapshot.
- `docs.command` is optional. Without it the docs gate reports `SKIP`, because generated docs and practices are already covered by the `source` gate.
- An explicitly empty `code.commands: {}` is allowed. When neither the config nor the scanner provides commands, the runner reports `WARN` and `dab detect` reports `verification.commands-empty`; neither is a fake pass. If the scanner detects commands while the config is empty, `dab detect` reports `verification.command-missing` instead.

`test` and `typecheck` are the scanner-required dimensions. When the scanner detects one of them and the config omits it, `dab detect` reports an error (`verification.command-missing`). The only waiver is an explicit entry with `mode: off`; deleting the key is not a waiver.

| Mode | Failure behavior |
|---|---|
| `required` | Runner exits non-zero; `dab detect --strict` treats missing required commands as errors. |
| `check` | Reports `WARN`; blocks only with `--strict`. |
| `advisory` | Reports `WARN`; blocks only with `--strict`. |
| `off` | Reports `SKIP`; explicit waiver, never a pass. |

`check` and `advisory` currently share runner behavior. Use `check` for a check the project intends to promote, and `advisory` for optional or expensive work.

## Commands and exit codes

```bash
node scripts/dab-check.mjs
node scripts/dab-check.mjs --strict
node scripts/dab-check.mjs --json
```

- The runner executes `source` first, then every configured code and docs command. It does not short-circuit after a failure.
- Human output prints one `GATE <id> <STATUS>` line per gate and a final `GATE RESULT PASS|FAIL exit <code>` line.
- `--json` prints `{ schemaVersion, gates, ok }`. Each gate has `id`, `status`, `required`, `command`, `exitCode` and `durationMs`; command output is streamed only in human mode and is not included in JSON.
- `0`: every required gate passed; check and advisory gates may warn.
- `1`: at least one required gate failed, or `--strict` promoted a warning.
- `2`: invalid or missing snapshot, an unresolved command, a missing DAB binary or another runner error.

Every gate status is one of `PASS`, `FAIL`, `WARN`, `SKIP`, `CONFIG` or `ERROR`. `CONFIG` covers a `command: null` entry and an invalid or missing snapshot; a missing DAB binary is `ERROR`. Both exit `2`, and `CONFIG` exits `2` regardless of the entry mode. Use `mode: off` to waive a command explicitly.

## Detect integration

`dab detect` adds a project-only `Verification` group that checks the config, runner, snapshot, command wiring and CI reference without executing project commands. `dab detect --strict` is the fixed `source` gate.

- Missing config, runner or snapshot and stale unmodified artifacts are warnings that fail `--strict`.
- Invalid, unreadable or malformed config is an error: `verification.config-invalid`, `verification.config-unreadable` or `verification.config-yaml`.
- A required command that the scanner detects but the config omits is `verification.command-missing`, an error.
- An unresolved command is `verification.command-needs-config`, a warning that fails `--strict`; the runner reports `CONFIG`.
- Modified, unversioned and newer runner or snapshot files are preserved and stay non-strict: `verification.runner-modified`, `runner-unversioned`, `runner-newer`, `snapshot-modified`, `snapshot-unversioned` and `snapshot-newer`.
- A missing CI reference is `verification.ci-missing`, non-strict. No commands at all is `verification.commands-empty`, non-strict.
- `verification.artifact-path` is an error when a managed gate path is not a regular file or would escape the project; `verification.artifact-concurrent-change` is a normalize-time warning when a file changed between planning and writing.
- `verification.starter-invalid` means scanner defaults produced an invalid starter; report it as a DAB bug.

When upgrading an existing project, run `dab normalize` before `dab detect --strict` so missing or stale gate artifacts are created or refreshed. Preserved modified, unversioned and newer artifacts need manual review.

The empty-command warning can differ between tools: `dab detect` keeps `verification.commands-empty` non-strict because it describes project state, while `node scripts/dab-check.mjs --strict` turns the runner's `WARN` into exit `1`.

## Stack detection

`dab init` and `dab normalize` detect these stacks without executing build tools:

| Stack | Evidence | Starter commands |
|---|---|---|
| Java Maven | `pom.xml`; `mvnw` or `mvnw.cmd` | `./mvnw test` and `./mvnw -DskipTests compile`, or `mvn` equivalents. |
| Java Gradle | `build.gradle[.kts]` or `settings.gradle[.kts]` without the Android plugin | `./gradlew test` and `classes`, or `gradle` equivalents. |
| Android | Android Gradle plugin or `app/src/main/AndroidManifest.xml` | `./gradlew test`, `lint`, `assembleDebug`; unit tests, not connected tests. |
| iOS SwiftPM | `Package.swift` | `swift test`, `swift build`; `swiftlint` when `.swiftlint.yml` exists. |
| iOS Xcode | `*.xcodeproj` or `*.xcworkspace`; `Podfile` and `Cartfile` are additional evidence | `needs-config` for test; no guessed scheme or destination. |
| Node, Python, Go, Rust | Existing lockfiles and build files | Existing scanner behavior. |

- Wrappers are preferred. On Windows the runner maps `./mvnw` to `mvnw.cmd` and `./gradlew` to `gradlew.bat`.
- Maven plus Gradle/Android is ambiguous and stays `needs-config` with a scanner warning; keep one build system or set an explicit command.
- Android suppresses duplicate Java Gradle commands. SwiftPM wins over Xcode evidence; an Xcode-only project is always `needs-config`.
- The starter selects one primary stack and one command per dimension. A mixed repository that needs commands from more than one stack must override `.agents/gates.yaml`; v1 has no multi-command dimension.

## Xcode and Fastlane

Xcode test and build commands must be explicit. Do not rely on a guessed scheme, configuration or simulator.

```yaml
      test:
        xcodebuild:
          workspace: App.xcworkspace
          scheme: App
          destination: platform=iOS Simulator,name=iPhone 16
        mode: required
```

If the project uses Fastlane, write a normal command instead:

```yaml
      test:
        command: bundle exec fastlane test
        mode: required
```

- Commit the scheme as a shared scheme.
- Without exactly one of `project`/`workspace`, plus `scheme` and `destination`, or a Fastlane command, `.agents/gates.yaml` keeps `command: null` and a `needs` explanation. `dab detect` reports `verification.command-needs-config` and the runner reports `CONFIG`; it never reports a fake pass.
- DAB does not run `xcodebuild -list` or `xcrun simctl list`; choose the destination yourself.

## CI

DAB does not generate CI files. Add the same runner to the CI provider manually so local and CI behavior match:

```yaml
- run: node scripts/dab-check.mjs --strict
```

GitLab CI example:

```yaml
gate:
  script:
    - node scripts/dab-check.mjs --strict
```

`dab detect --strict` reports a non-strict `verification.ci-missing` warning when no recognized CI file references `scripts/dab-check.mjs`. CI wiring is provider-neutral; DAB does not require GitHub Actions.
