# Agent Note: Project gates

Status: implemented

English | [中文](2026-11-25-g1-gates.zh.md)

## Problem

DAB could generate docs, notes and managed authoring skills, and `dab detect --strict` could find configuration drift. It did not give a consuming project a stable local execution entry point. Generated practices could remain unrun, `detect` was a checker rather than a daily command, Java/iOS/Android projects had no command adaptation, and there was no place for a same-change check. G1 was the highest execution-layer gap after G4 closed managed skill updates in 0.1.2.

## Decision

- `.agents/gates.yaml` is authored and project-only. It has a strict version-1 schema, a fixed `required` source gate, and `code` commands named `test`, `typecheck`, `lint` and `build`. `docs` requires a `mode`; only its command is optional. Modes are `required`, `check`, `advisory` and `off`.
- `scripts/dab-gates.json` is a generated snapshot compiled by normalize from the authored config. Scanner output only seeds a missing starter and never backfills an existing config. Its SHA-256 covers the canonical `gates` object. `scripts/dab-check.mjs` is a stable runner with a `// dab-gate-runner: <version> sha256=<hash>` marker. The runner reads the snapshot, embeds no project commands, and does not parse YAML. This keeps the runner stable while commands remain reviewable configuration.
- The runner executes the fixed `source` gate first (`dab detect --strict`), then every configured code and docs command without short-circuiting. `DAB_BIN`, local `node_modules/.bin/dab`, `PATH` and `npx --no-install @saydone/dab` are the only binary resolution paths. A missing DAB binary is `ERROR`; an unresolved command or invalid/missing snapshot is `CONFIG`; both exit `2`. Required failures exit `1`; `--strict` also promotes check and advisory warnings. `mode: off` is an explicit `SKIP` waiver, and a dropped scanner-required `test`/`typecheck` is a detection error unless it is explicitly off.
- Init and normalize create missing gate files. Normalize replaces only an unmodified older runner or a stale snapshot; modified, unversioned and newer generated files are preserved with warnings. A file changed between planning and applying is preserved as `verification.artifact-concurrent-change`. Invalid authored config blocks every write, so DAB never writes a partial gate set.
- The scanner detects Node, Python, Go, Rust, Java Maven, Java Gradle, Android, iOS SwiftPM and iOS Xcode by reading files only. Maven and Gradle prefer wrappers (`mvnw`/`gradlew`, Windows `.cmd`/`.bat` at runner time); Android suppresses duplicate Java Gradle commands; SwiftPM suppresses Xcode test commands. An Xcode-only project stays `needs-config` with `command: null` and a `needs` explanation until the project supplies exactly one of `project`/`workspace` plus `scheme` and `destination`, or a Fastlane command. DAB does not run `xcodebuild -list` or choose a simulator.
- `dab detect` adds a project-only `Verification` group. Missing config, runner or snapshot and stale unmodified artifacts are warnings that fail `--strict`. Invalid, unreadable or malformed config is an error, as are `verification.command-missing` and `verification.artifact-path`. `verification.command-needs-config` fails `--strict`. Modified, unversioned and newer artifacts, `verification.commands-empty` and `verification.ci-missing` stay non-strict. `verification.starter-invalid` reports a DAB bug.
- G1 adds no `dab` command. The source gate reuses `dab detect --strict`, and projects call the generated runner from their own CI. DAB does not generate CI files, does not probe build tools, and does not implement the G9 change gate.

## Alternatives considered

**Add `dab check` as a new CLI command.** Rejected: G1 requires no new command, and a project-local runner must work in CI without making DAB the only entry point.

**Embed project commands in the generated runner.** Rejected: every command edit would rewrite executable code, review would compare code instead of configuration, and the runner would diverge from the stable-runner pattern used by pre-commit, Nx and Turborepo. The snapshot keeps commands declarative while the runner stays stable.

**Generate only a shell script.** Rejected: Java and Android projects may use Windows, and Node is already a DAB prerequisite. The runner normalizes `./mvnw` and `./gradlew` on Windows; DAB's own v0.1 CLI still rejects Windows, so full gate support there waits for platform support.

**Generate a CI workflow automatically.** Rejected: CI providers, permissions, branch policy and release pipelines differ per project, and a workflow is security-sensitive. v1 documents snippets and emits a non-strict `verification.ci-missing` warning.

**Run `xcodebuild -list` or `gradle tasks` during init.** Rejected: those probes can need SDKs, network or time and still do not prove the project's intended destination. Explicit project configuration is the contract.

**Copy deepseek-harness's `check:all`.** Rejected: its gate list is project-specific. DAB reuses the aggregation mechanism and stack adaptation, not business commands.

## Consequences

- A project gets one local and CI entry point, `node scripts/dab-check.mjs`, with `--strict` and `--json`. Local and CI parity comes from running the same file, not from a generated workflow.
- The source gate requires a DAB binary. Without one the runner reports `ERROR` and exits `2` instead of skipping DAB checks.
- Xcode projects are intentionally not zero-config: an unconfigured project reports `verification.command-needs-config` and runner `CONFIG` until a person supplies a shared scheme and destination or a Fastlane command.
- The starter selects one primary stack and one command per dimension. A mixed repository that needs test commands from more than one stack must override `.agents/gates.yaml`; v1 has no multi-command dimension.
- Modified, unversioned and newer gate artifacts stay in place until a person reconciles them. Normalize never overwrites or downgrades them, so `detect` can keep warning.
- Empty config plus empty scan is only a warning. `detect` keeps `verification.commands-empty` non-strict because it describes project state, while the runner's `--strict` turns its `WARN` into exit `1`; the two tools intentionally differ.
- CI wiring remains manual and missing CI is non-strict, so a project can adopt gates locally before touching its pipeline.
- G1 is implemented on `main` before a release; `package.json` is not bumped and no tag is created. The G9 change gate, an opt-in CI generator and eval evidence remain deferred.
